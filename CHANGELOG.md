# Changelog

## 1.4.0 - 2026-11-18

Fixed (1.4.0-beta.11): Show when - every re-check is registered in the capped waiting list (20, the oldest tracked dropped) when its event is tracked, and runs only if it is still there when the event is delivered. A delivery that waited behind a failing flush and then succeeded used to run its re-check directly, skipping the cap; iOS kept to 20 only by timing. It now holds by construction, as on Android and the web.

Fixed (1.4.0-beta.10): Show when - past 20 waiting re-checks the OLDEST tracked is dropped, whatever order the failed deliveries come back in. Each tracked event re-checks in a Task of its own; the waiting list is now kept in tracking order (a stamp taken when the event is tracked), as on Android, where the out-of-order case was found.

Added (1.4.0-beta.9): "Show when" for placement campaigns (Joryio BACKLOG D465) - the moment a campaign's content is revealed on a screen. `Placements.SHOW_WHEN_KINDS` lists the wire kinds (`load`, `seconds`, `scroll`, `exit`, `event`). An item's `showWhen` is honoured: the SDK fetches it as before and HOLDS it - it is not in `getPlacements`, `onPlacementsUpdated` or `PlacementView` - until its moment, then `onPlacementsUpdated` fires and the view draws it. `{ kind: 'seconds', seconds }` counts foreground seconds on the current screen, on the same clock as the `time_on_screen` in-app trigger (the screen is the last `trackScreen`; background time does not count). `{ kind: 'event', event }` is met once that event was tracked in this visit (the SDK session), before or after the answer arrived; when such an event is tracked the SDK asks again at once for the placements that wait on it (or list it in the answer's `recheckOn`), past the 30 s refresh limit, at most once per placement and event per screen - and only after the event has left the event queue: it waits for a flush already in flight, flushes again, and after a failed flush runs the re-check once after the next successful one. The re-check is a request of its own that carries the event as `recheckEvent: { name, eventId, properties }` (the event's client `eventId` and properties as queued), which the server counts as the arriving event, so an audience condition such as "did Add to cart" counts at once. A re-check still waiting for its event runs only for the person and consent it was made for: it is dropped on identify, reset, a consent change or opt-out, a new screen, and after 60 s, and at most 20 wait at once (the oldest is dropped). `scroll` and `exit` are web-only; such an item, an unknown kind or an invalid value is never shown (never treated as "on load"). Revealed content stays for the screen; a new screen holds it again until the new screen's moment (an event of this visit still counts at once). An impression (`markDisplayed`) counts only once the item is revealed. A held-out answer (`isControl`) with a `showWhen` reports `control_viewed` only after that moment: `Placement.markDisplayed()` before it is ignored, and `onPlacementsUpdated` fires at the moment so the app can call it again. `deferredControls` on a filled answer are each reported once as `control_viewed` (the same body, with their own `controlToken`) once their moment has come and the spot was viewable on this screen (a drawn item's impression, or any `markDisplayed()` of that placement); `PlacementView` now reports an empty spot's viewability for this. An answer to an older request that arrives after a newer one is no longer applied. The legacy event `triggers` window is unchanged. There is no capability flag: placements exist only in the 1.4.0 betas, so an older beta (1.4.0-beta.8 and earlier) receives such a campaign and shows it as soon as the screen loads. The same feature on Android; React Native and Unity inherit it from the native SDKs; web adds `scroll` / `exit` and Web personalization (page edits).

Fixed (1.4.0-beta.6): a beta reports its own version. The release build writes the beta (`1.4.0-beta.6`) into `SDK_VERSION` (and so `JoryioVersion`) of the public repository's tag, not only into the podspec: it is sent as `X-Joryio-SDK-Version`; before, every beta said `1.4.0`. The same fix on web, Android, React Native and Unity.

Changed (1.4.0-beta.5): one subscription type for every listener, the same on all five SDKs (Joryio BACKLOG D444 / D446, owner decisions 2026-11-23). `onCardsUpdated`, `onPlacementsUpdated` and `onFlagsUpdated` return a `JoryioSubscription` (`cancel()` stops the updates, twice is harmless). It replaces `CardsSubscription`, `PlacementsSubscription` and `FlagsSubscription` - the same type name and `cancel()` as on Android, web, React Native and Unity. `onPlacementsUpdated` before `initialize()` now logs an error (nothing is registered, as before), like `onFlagsUpdated` and `onCardsUpdated`. Content cards: `attachCardFeedListener(_:)` is SDK-internal now (`@_spi(JoryioInternal)`, like `LinkRouter`). It was the feed views' and bridges' variant that answers nil before `initialize()`; an app listens with `onCardsUpdated(_:)`, the one listener every Joryio SDK has, and no other SDK exposes an equivalent. SwiftUI `JoryioCardFeed` takes `pinnedLabel`, `dismissLabel` and `unreadLabel`, like `CardFeedViewController` and the feeds on Android, web and React Native, so a localized SwiftUI app can translate them. Neither placements, flags nor cards are in a final release (none of the three listeners exists in 1.3.3), so the breaking renames are made now. No wire changes.

Added: `PlacementView` and SwiftUI `JoryioPlacement` draw an item's recommended products (Joryio BACKLOG D444) - a horizontal row of product cards (image, title, price with the compare-at price struck through, optional button) below the item's content, or alone for a data item; system semantic colours, `tintColor` and Dynamic Type. A tap reports `clicked` with elementId `product:<id>` and opens the product link like a `deep_link` button, through `setLinkHandler` first (source `placement`). Options `showProducts` (default true), `productButtonText`, `productCardWidth`. New `Placements.PLACEMENT_PRODUCT_ELEMENT_PREFIX`, `PLACEMENT_PRODUCT_CARD_WIDTH`, `placementProductElementId(_:)`.

Added: the `time_on_screen` in-app trigger (Joryio BACKLOG D444 follow-up; the app equivalent of the web's `time_on_page`, contract `packages/backend/src/common/in-app-screen-triggers.ts`). A campaign shows once the person has been on a screen for `value` seconds - the screen named by the trigger's `screenName` (trimmed, case-insensitive) or any screen. The clock (`ScreenClock`) starts at `trackScreen` / a `Screen Viewed` event: a new name restarts it, the same name again does not, background time does not count, and each campaign fires once per screen visit through the usual display gates. `InAppTrigger.screenName` is new; /sync now declares the `screen_context` capability (also when a host renderer draws), and the server sends such campaigns only to SDKs that declare it.

Added: one app-wide link handler, `Joryio.shared.setLinkHandler { link in ... }` / `clearLinkHandler()` (safe before `initialize()`), that receives EVERY link the SDK is about to open - an in-app message button or link, a `PlacementView` button or link, a card tap, a push tap - http(s) and app deep links alike, as a `JoryioLink` (`url`, `source`: `JoryioLinkSource` `in_app` / `placement` / `card` / `push`, `campaignId`, `placementKey`, `itemId`, `cardId`, `isAppDeepLink`). Return true to take it over, false for the behaviour without a handler; `link.openDefault()` runs that behaviour later (at most once). Refused schemes (`javascript:`, `data:`, `file:`, ...) never reach the handler nor the system; a push link no longer opens one either. Existing `onDeepLink` handlers keep receiving app deep links, after the app-wide handler declines. An in-app message's app deep link (`deep_link` button with `myapp://...`) now reaches the handler; without one it is not opened, as before. New `JoryioConfig.forwardUniversalLinks` (default false): an https link whose host is one of the app's associated domains (`applinks:` entries from its own code signature, `*.domain` wildcards matching subdomains) goes to the app's own universal-link handling - an `NSUserActivityTypeBrowsingWeb` activity to the scene delegate's `scene(_:continue:)` or the app delegate's `application(_:continue:restorationHandler:)` - instead of `UIApplication.open`, which usually sends the app's own link to Safari; when the entitlements cannot be read the link opens as before (logged once). The same names and source values on all five SDKs.

Added: content cards and the inbox (Joryio BACKLOG D444 Phase 3, docs/PLACEMENTS_PLAN.md section 11) - a persistent feed per person, filled from card campaigns and the journey step "Add card". JoryioUI: `CardFeedViewController` (UIKit) and `JoryioCardFeed` (SwiftUI) - a plain scrolling list: image, title, body, optional button, a "Pinned" marker, an unread dot and a dismiss control with an accessible label, "No messages yet" when empty - all overridable - in system fonts and semantic colors. The view reports `viewed` then `read` once half a card was on screen for a second (the placement viewability rule, now one shared helper), `clicked` on a tap (then opens the url: http(s) in the system, an app deep link through `onDeepLink`, refused schemes never) and `dismissed` on the x, and loads the next page near the end. Data first: `Joryio.shared.getCards(cursor:completion:)` and `async getCards(cursor:)` returning `CardFeed { cards, unreadCount, nextCursor, stateScope }`, `getUnreadCardCount()` (from the cache), `markCardViewed` / `markCardRead` / `markCardClicked` / `dismissCard` (a `Card` or its id), `refreshCards()`, `onCardsUpdated(_:)` (returns a `JoryioSubscription`); constants `Cards.CARD_FEED_TTL_SECONDS` (300) and `Cards.CARD_MIN_REFRESH_SECONDS` (30). One `POST /v1/in-app/cards` per refresh (no retries), the feed cached on disk per person for the TTL, at most one request per 30 s (extra calls coalesce), `notModified`, `success: false` and a 429 keep the cache; refreshed on foreground after the TTL, identity and consent changes and the silent push `jry_sync: "cards"`. Reports are `POST /v1/in-app/track` with `{ deliveryToken, action, sessionId }`, each action once per card, applied to the cache at once. An anonymous visitor's read / dismissed ids (`stateScope: "device"`) are kept on the device and cleared on identify / reset / wipeData. Without tracking consent nothing is requested or reported. New sync capability `cards`. The same names and wire values on all five SDKs.

Added: placements (Joryio BACKLOG D444, docs/PLACEMENTS_PLAN.md) - named spots inside your app that Joryio fills per person from placement campaigns and journey steps. JoryioUI: `PlacementView(placementKey:)` (UIKit) and `JoryioPlacement(_:)` (SwiftUI) draw native items as a card and HTML items (only delivered with `allowHtmlJsInAppMessages`) with no script, measure viewability (`Placements.PLACEMENT_VIEWABLE_FRACTION`, 0.5, for `InAppDisplay.IN_APP_DISPLAY_DWELL_MS` while the app is active) and report impressions, clicks, dismissals and the holdout's `in_app.control_viewed`; content is never swapped while the view is on screen. Data first: `Joryio.shared.getPlacements(_:completion:)` and `async`, `refreshPlacements(_:)`, `onPlacementsUpdated(_:)` (returns a `JoryioSubscription`), `item.markDisplayed()` / `markClicked(elementId:)` / `markDismissed()`, `placement.markDisplayed()`. One `POST /v1/in-app/placements` per 50 ms batch (up to 10 keys), answers cached on disk for `ttlSeconds` per person, at most one fetch per key per `Placements.PLACEMENT_MIN_REFRESH_SECONDS` (30), a 429 keeps the cache; refreshed on foreground after the TTL, identity and consent changes and the silent push `jry_sync: "placements"` (also `in_app`). Without tracking consent the request names nobody and nothing is reported. New sync capabilities `placements` and `content.data`. The same names and wire values on all five SDKs.

Fixed: content cards (D444, not released yet) - the stored feed and an anonymous person's read / dismissed state are per workspace, like the placements cache: the keys now carry the SDK key (`jry_<sdkKey>_cards_cache`, `jry_<sdkKey>_cards_device_state`), so an app that switches SDK keys never reads the other workspace's cards. The old unscoped `cards_cache` and `cards_device_state` are never read and are removed on start. No wire changes.

Fixed: placements (D444, not released yet) - the stored answers are per workspace, like the flags answer below: the key now carries the SDK key (`jry_<sdkKey>_placements_cache`), so an app that switches SDK keys never reads the other workspace's placements. The old unscoped `placements_cache` is never read and is removed on start. No wire changes.

Fixed: feature flags (D446, not released yet) - the stored answer is per workspace. It was kept under one key in the app's one database, so an app that switches SDK keys could read the other workspace's flags for the same user id. The key now carries the SDK key, like every other stored key; the old `flags_cache` is never read and is removed at start. No wire changes.

Added: feature flags and remote config (Joryio BACKLOG D446). `getFlag(_:default:)` and the typed `getBoolFlag`, `getStringFlag`, `getNumberFlag` (`Double`), `getJsonFlag(_:default:)` / `getJsonFlag(_:as:default:)` (`Decodable`) return the value Joryio decided for this person, or your in-code default before the first answer, for a flag Joryio did not send, for a value of another type, or without tracking consent; they never wait for the network. `getAllFlags()` (logs no exposure), `refreshFlags()` (async, and `refreshFlags(completion:)`) and `onFlagsUpdated(_:)` (main thread, returns a `JoryioSubscription` to `cancel()`). Nothing is fetched until the app uses flags; then one `POST /v1/flags/evaluate` returns every flag, kept on the device for the same person only (`wipeData()` erases it) and refreshed at start, on foreground (at most once per `JoryioFlags.FLAGS_MIN_REFRESH_SECONDS`, 60), on identify / reset, on a consent change, on the silent push `jry_sync: "flags"` and on `refreshFlags()`, with the `etag` so an unchanged answer is not sent again. The first read of a value in a session logs an exposure (`POST /v1/flags/exposures`, batched, once per person, flag and variant per session, skipped when the answer says `logExposure: false`); each batch is sent as the person who read the values and dropped when consent is withdrawn first. The same names and wire values on all five SDKs.

Added: every request names the SDK and its version - `X-Joryio-SDK: ios` and `X-Joryio-SDK-Version: <version>` - including the push click and delivery receipts (BACKLOG D427). A React Native or Unity bridge calls `Joryio.setSdkWrapper(name:version:)` before `initialize`, and its requests also carry `X-Joryio-SDK-Wrapper` (`react-native` / `unity`) and `X-Joryio-SDK-Wrapper-Version`. Settings > Apps shows the oldest version each app ran in the last 7 days and when a newer SDK is out. `setSdkWrapper` is for Joryio's own bridges; an app never calls it. Sending `X-Joryio-SDK: ios` also lets the backend apply the key-platform check (contract item 60) to iOS, which this SDK already enforces locally. The same wire names on all five SDKs.

Added: `resetTo(_:)` (safe before `initialize()`, like `reset()`) - everything `reset()` does, then the anonymous id you pass instead of a random one, for an app that keeps its own visitor id (BACKLOG D366). The id must be 8 to 255 letters, digits, `.`, `_`, `:` or `-`, must not have the shape of a Joryio profile id (24 lowercase hex) and must not be the user id the SDK holds; a refused id is logged and the call is a plain `reset()` (a random id), so a logout is never skipped. The same name and rule on all five SDKs. No wire changes: the server sees an ordinary anonymous id. Like `reset()`, `resetTo` drops a click-link token the SDK has not sent yet (one held while consent is pending), so the link is never attributed to the next person on the device.

Changed (BACKLOG D366, before any release of resetTo): it also refuses the anonymous id the SDK holds while a user is signed in - that id is tied to the signed-in person's profile, and adopting it would hand their in-app messages, events, form attribution and push subscription to the next person on a shared device (a random id is used instead). `resetTo(_:onResult:)`: `true` adopted, `false` refused; a call held before `initialize()` answers when it runs. The same on all five SDKs.

Changed (BACKLOG D366): `resetTo` also refuses the last 20 anonymous ids this device held for a signed-in user when a reset signed them out (stored locally, newest kept; `wipeData()` forgets them) - a random id is used and it answers `false`, the same message and cap on all five SDKs. A `resetTo` held before `initialize()` and discarded before it runs (pushed out of a full buffer) now answers `false`, exactly once.

Added: `identifyFromLink(_ url: URL)` (safe before `initialize()`) - click-link identity. Pass the universal link / deep link that opened the app; when it carries the `jr_t` token a tracked Joryio message link adds, the SDK sends it with the anonymous id to `POST /v1/identify-link`. The server uses it only to attribute this app's session and later events (Session Start, screen views, conversions) to the contact the message was sent to - it never identifies the person: the app's profile does not become the contact and is never merged into it, and nothing set in the app is written to the contact. Only `identify` joins the two. Nothing happens when a user is identified, the person opted out or consent is denied; while consent is pending the token is held in memory and sent on `.granted`. The token is never persisted or logged above debug, and the same token is sent once per launch. The same name, parameter, path and body (`token`, `anonymousId`) on all five SDKs.

## 1.3.3 - 2026-11-03

Fixed: an in-app message counted as displayed the moment it was drawn, so one that flashed up during a screen change, or as the app went to the background, was reported `displayed` and used up the campaign's frequency cap although nobody saw it. A message the SDK draws now counts - reporting `displayed` and spending the cap - only after it has been on screen for `InAppDisplay.IN_APP_DISPLAY_DWELL_MS` (1000 ms) while the app stayed active. If the app leaves the foreground first, nothing is reported or spent; with the message still up when the app returns, the wait starts again. A tap or a dismiss sooner means the person saw it: `displayed` is reported first, then `clicked` or `dismissed`. A message dropped by a reset or an identity, opt-out or consent change before it counted reports nothing. Messages are also drawn only onto a settled screen - app active, top view controller in its window and not being presented, dismissed, pushed or popped; one that finds no settled screen within 10 seconds is not drawn and is tried again when the app next becomes active. `onMessageDisplay` fires when the message counts. Apps that draw messages themselves should report `displayed` by the same rule. The same rule and constant on every Joryio SDK; the wire is unchanged.

Changed: CocoaPods is deprecated in favour of Swift Package Manager. CocoaPods trunk stops taking new versions (it refused pushes in its read-only test week and is read-only from 2 December 2026), so a release may not be on trunk. CocoaPods users install from this repository's git tag instead, which needs no trunk and works for every release from 1.3.0: `pod 'Joryio/UI', :git => 'https://github.com/joryio/joryio-ios-sdk.git', :tag => '1.3.3'`. Swift Package Manager is unchanged and remains the recommended way.

## 1.3.2 - 2026-10-25

Added: `InAppConfig.holdInAppMessagesForHandler` (off by default). An app that draws in-app messages itself and calls `setInAppMessageCallback` after `initialize()` could have the first message drawn by the SDK: the sync `initialize()` starts could finish before the callback was set. With the option on, a message that is ready before the callback is held - not drawn, not reported, nothing spent, keeping the display slot - and handed to the callback when it is set; `clearInAppMessageCallback()` instead ends the hold and the SDK draws the held message. A reset or an identity, opt-out or consent change drops a held message. A `clearInAppMessageCallback()` made before a deferred `initialize()` (first unlock) is now applied at init too. A held message is bound to the person it was chosen for: delivery re-checks the anonymous id, user id and age (at most 5 minutes) as well. The same option, by the same name, on Android, React Native and Unity.

## 1.3.1 - 2026-10-24

Fixed: apps with an iOS 14 deployment target failed to build when Swift Package Manager resolved SQLite.swift 0.17.0 or newer (it requires iOS 15; reported by Xcode 16.3 and later). The package now accepts SQLite.swift from 0.15.0 up to, but not including, 0.17.0, so a fresh resolve picks 0.16.x.

Fixed: an HTML modal or slide-up could grow but never shrink - a modal started at 240pt, so an 80pt message kept a 240pt frame. The height is now measured from the message body, so a short message is as short as its content and a message re-fits when it gets shorter (a form replaced by its thank-you line). Heights stay capped at 90% of the screen; the message now scrolls inside beyond the cap instead of being cut off.

Added: `InAppCampaign.maxWidth` for HTML modals and slide-ups (points, set by the "Max width" field in the dashboard; modal 600 and slide-up 400 when unset), with `InAppSizing` helpers. `JoryioUI` lays a modal out centred at min(maxWidth, width - 2x24) and a slide-up at min(maxWidth, width - 2x12), and re-fits on rotation and split view. Before, these messages were full width on iPad.

Swift Package Manager is the supported way to install the SDK; see the README for moving from CocoaPods.
